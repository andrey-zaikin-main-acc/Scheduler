# Алгоритм планирования MVP

## Цель

Алгоритм строит производственный план по заказам так, чтобы выполнить заказы к сроку отгрузки и разместить операции максимально поздно от срока отгрузки назад. Если заказ невозможно выполнить в срок, алгоритм фиксирует конфликт планирования.

## Зафиксированные правила

- Планирование выполняется по дням, каждый день считается рабочим.
- Внутри расчёта потребность хранится в часах, включая дробные значения.
- Дробные часы отображаются в интерфейсе с округлением до 2 знаков.
- Производство в день отгрузки разрешено: отгрузка считается в конце дня.
- По умолчанию операции не размещаются раньше текущей даты.
- Для тестов разрешены заказы со сроком отгрузки в прошлом.
- Технический предел поиска назад — 12 месяцев.
- Операция может размещаться с разрывами по дням.
- Операции одного заказа могут пересекаться в один день на разных участках, если соблюдена передаточная партия.

## Статусы заказов

В планирование включаются заказы со статусами:

- `Новый`;
- `Запланирован`;
- `Не выполнен`;
- `Конфликт планирования`.

Не включаются:

- `Выполнен` — исключается из пересчёта, но остаётся в реестре;
- `Отменён` — не участвует в планировании, мощности освобождаются.

Для статуса `Не выполнен` в MVP весь заказ возвращается в планирование. Частичный факт выполнения не учитывается.

## Расчёт потребности

Для каждой операции маршрута:

```text
required_hours = order_quantity × labor_hours_per_1000 / 1000
```

Суммарная трудоёмкость заказа:

```text
total_required_hours = сумма required_hours по всем операциям маршрута
```

Трудоёмкость операции должна быть больше 0. Если у маршрута нет операций, заказ нельзя запланировать.

## Сортировка заказов

При полном пересчёте заказы сортируются так:

1. раньше срок отгрузки;
2. больше суммарная трудоёмкость;
3. ID заказа.

Формально:

```text
shipment_date ASC, total_required_hours DESC, order_id ASC
```

## Модель мощности

Для каждого участка и дня алгоритм рассчитывает:

```text
free_hours = available_hours_per_day - occupied_hours
```

На форме участка нужно запрещать 0 и отрицательные значения доступных часов. В расчёте дополнительно должна быть защита от некорректной мощности.

## Размещение операции

Операция размещается максимально поздно относительно своего дедлайна.

Алгоритм идёт назад по дням:

```text
remaining_hours = required_hours
date = latest_allowed_date

while remaining_hours > 0:
    free_hours = capacity[work_center][date]
    placed_hours = min(remaining_hours, free_hours)
    reserve placed_hours
    remaining_hours -= placed_hours
    date = date - 1 day
```

Если в допустимом окне не хватает свободных часов, создаётся конфликт.

## Частичная передача партии

Передаточная партия задаётся на переходе между двумя операциями маршрута.

Если тираж заказа меньше передаточной партии, передаётся весь тираж:

```text
effective_transfer_quantity = min(order_quantity, min_transfer_quantity)
```

MVP использует упрощённую модель: следующая операция может стартовать после накопления первой минимальной партии на предыдущей операции.

Время накопления первой партии:

```text
hours_to_first_transfer = effective_transfer_quantity × previous_operation_labor_hours_per_1000 / 1000
```

## Конфликт планирования

Конфликт фиксируется, если заказ или операция не могут быть размещены в допустимом окне.

Конфликт должен содержать:

- ID заказа;
- срок отгрузки;
- ограничивающий участок;
- требуемые часы;
- свободные часы в допустимом окне;
- дефицит мощности;
- мешающие заказы;
- краткое объяснение причины.

Дефицит:

```text
deficit_hours = required_hours - free_hours_in_allowed_window
```

Мешающие заказы — заказы, занимающие ограничивающий участок в критическом периоде.

## Свободные слоты

Пользователь выбирает период анализа. По умолчанию используется ближайшие 30 дней.

Для участка и даты:

```text
free_hours = available_hours_per_day - occupied_hours
```

## Возможный тираж по маршруту

Для каждого участка маршрута:

```text
possible_quantity = free_hours_for_period × 1000 / labor_hours_per_1000
```

Возможный тираж маршрута:

```text
possible_route_quantity = min(possible_quantity по участкам маршрута)
```

## Пересчёт

Пересчёт запускается автоматически после сохранения изменений и вручную кнопкой «Пересчитать план».

Старый план — последний сохранённый план перед пересчётом. Перед пересчётом текущий план читается из SQLite, новый план строится заново, после чего сохраняется список изменений.
