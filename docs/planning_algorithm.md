# Алгоритм планирования MVP

## Цель

Алгоритм строит производственный план по заказам так, чтобы выполнить заказы к сроку отгрузки и разместить поток операций как можно позднее относительно дедлайна отгрузки. Если заказ нельзя разместить в допустимом окне, алгоритм фиксирует конфликт планирования.

## Зафиксированные правила

- Планирование выполняется по календарным дням, каждый день считается рабочим.
- Поле `available_hours_per_day` в схеме сохраняет месячную производственную ёмкость участка. Дневная доступная мощность для конкретной даты рассчитывается как `available_hours_per_day / количество календарных дней в месяце этой даты`. Название поля осталось историческим.
- Поле `workday_start_time` сохраняется в модели и справочнике, но не влияет на дедлайн отгрузки и не используется для преобразования дневной мощности в календарную длительность.
- Внутри расчёта потребность хранится в часах, включая дробные значения.
- Дробные часы отображаются в интерфейсе с округлением до 2 знаков.
- Производство в день отгрузки разрешено, но сохранённый план не может выходить за календарную дату отгрузки: дата запуска и фактическое окончание последней операции должны быть не позже `shipment_date`.
- Расчётный дедлайн отгрузки равен концу календарной даты `shipment_date`; он не зависит от участка и `workday_start_time`.
- По умолчанию операции не размещаются раньше текущей даты.
- Для тестов и сервисного использования можно передать отдельную дату начала планирования.
- Технический предел поиска назад — `MAX_BACKWARD_SEARCH_MONTHS × 31` день от даты отгрузки.
- Операция может переходить на следующий рабочий день, но один батч операции размещается непрерывно по рабочему времени участка.
- Разрывы между батчами и операциями возможны из-за занятости участков.
- Операции одного заказа могут пересекаться по календарным дням на разных участках, если соблюдена готовность входного батча.

## Статусы заказов

В планирование включаются заказы со статусами:

- `Новый`;
- `Запланирован`;
- `Конфликт планирования`.

Не включаются:

- `Отменён` — не участвует в планировании, мощности освобождаются после пересчёта.


## Расчёт потребности

Для каждой операции маршрута:

```text
required_hours = order_quantity × labor_hours_per_1000 / 1000
```

Суммарная трудоёмкость заказа:

```text
total_required_hours = сумма required_hours по всем операциям маршрута
```

Трудоёмкость операции должна быть больше 0. Если у маршрута нет операций, заказ нельзя запланировать.

## Сортировка заказов

При полном пересчёте заказы сортируются так:

1. раньше срок отгрузки;
2. меньше ID заказа.

Формально:

```text
shipment_date ASC, order_id ASC
```

Суммарная трудоёмкость рассчитывается при подготовке заказа, но в текущей реализации не используется как ключ сортировки.

## Модель мощности

Для каждого участка и дня алгоритм рассчитывает:

```text
daily_available_hours = available_hours_per_day / days_in_month(date)
free_hours = daily_available_hours - occupied_hours
```

Технический интервал дня для батчей и диаграммы Ганта нормализуется внутрь календарной даты. Он нужен только для упорядочивания резервирований и пропорционального отображения занятой мощности; это не фактическое время смены. Например, резервирование половины дневной мощности занимает примерно половину календарной даты на технической шкале.

На форме участка поле подписано как «Доступное время в месяц»; запрещены 0 и отрицательные значения месячной мощности. В расчёте дополнительно есть защита от некорректной мощности.

## Размещение заказа

Текущая реализация планирует заказ как поток батчей вперёд во времени, но выбирает для него самый поздний старт, при котором весь поток успевает завершиться до дедлайна отгрузки.

Общая схема:

```text
latest_finish = конец календарной даты shipment_date
earliest_start = max(дата начала планирования, дата отгрузки - технический предел)
flow_duration = длительность маршрута на абстрактной временной шкале без календарных занятостей
candidate_start = latest_finish - flow_duration

while candidate_start >= earliest_start:
    пробно разместить батчи маршрута вперёд от candidate_start
    если последний батч завершился <= latest_finish
       и дата запуска <= shipment_date
       и дата фактического окончания последней операции <= shipment_date:
        сохранить найденное размещение
        stop
    откатить пробное размещение
    candidate_start -= 1 час
```

Для каждого батча операции алгоритм:

1. ждёт готовности входного количества;
2. при необходимости ждёт завершения предыдущего батча той же операции;
3. ищет самый ранний непрерывный свободный интервал на участке;
4. резервирует интервал вперёд по рабочему времени, перенося остаток на следующие дни.

## Минимальная партия операции

Поле схемы называется `min_transfer_quantity_to_next`, но текущий планировщик трактует сохранённое значение как минимальную стартовую партию текущей операции.

Правила батчевания:

- если `min_transfer_quantity_to_next` заполнено, операция стартует батчами этого размера;
- последний батч может быть меньше минимальной партии;
- если значение не заполнено, операция обрабатывает весь доступный входной объём одним батчем;
- значение, если задано, должно быть больше 0.

На абстрактной шкале сначала считается потребность батча в мощности, затем она переводится в долю нормализованного календарного дня конкретного участка:

```text
batch_hours = batch_quantity × labor_hours_per_1000 / 1000
normalized_duration = batch_hours / daily_available_hours × normalized_calendar_day
```

Следующая операция может начать батч только после того, как соответствующее входное количество стало готово на предыдущей операции.

## Конфликт планирования

Конфликт фиксируется, если заказ или операция не могут быть размещены в допустимом окне, если входные данные заказа некорректны, либо если найденное размещение нарушает дедлайн отгрузки. Перед сохранением успешного результата сервис повторно проверяет, что `calculated_start_date <= shipment_date` и максимальный `end_datetime` среди дней операций не позже календарной даты отгрузки; при нарушении заказ переводится в `Конфликт планирования`, а `calculated_start_date` очищается.

Конфликт содержит:

- ID заказа;
- срок отгрузки;
- ограничивающий участок, если его можно определить;
- требуемые часы;
- свободные часы в допустимом окне;
- дефицит мощности;
- мешающие заказы;
- краткое объяснение причины.

Дефицит:

```text
deficit_hours = max(0, required_hours - free_hours_in_allowed_window)
```

Мешающие заказы — заказы, занимающие ограничивающий участок в критическом периоде.

## Очистка устаревших расчётных дат

Расчётные поля заказа не считаются пользовательским вводом. При изменении полей, влияющих на план (`quantity`, `shipment_date`, `route_id`, `status`), репозиторий очищает `calculated_start_date` до пересчёта, чтобы в реестре не оставалась дата запуска от предыдущего варианта заказа. После полного пересчёта дата либо заполняется новым успешным планом, либо остаётся пустой вместе со статусом `Конфликт планирования`.

## Свободные слоты

Сервис свободных слотов рассчитывает активные участки за выбранный пользователем включительный период. По умолчанию используется ближайшие 30 дней.

Для участка и даты:

```text
daily_available_hours = available_hours_per_day / days_in_month(date)
free_hours = max(0, daily_available_hours - occupied_hours)
```

`occupied_hours` берётся из сохранённых дневных размещений плана.

## Предварительная проверка тиража и слотов отгрузки

В реестре заказов есть предварительный расчёт по активному маршруту за выбранный включительный период. Он запускается только отдельной кнопкой «Рассчитать доступный тираж»: обычное открытие или перерисовка реестра не вызывает расчёт мощности. Результат хранится в состоянии страницы вместе с маршрутом, началом и окончанием периода и показывается только пока эти параметры совпадают с текущими. Расчёт не создаёт заказ, не сохраняет плановые операции и не меняет текущие данные плана.

Для каждой операции активного маршрута:

```text
possible_quantity = free_hours_for_period_on_operation_work_center × 1000 / labor_hours_per_1000
```

Теоретический возможный тираж маршрута:

```text
theoretical_route_quantity = floor(min(possible_quantity по операциям маршрута))
```

Затем сервис бинарным поиском снижает теоретический предел до максимального целого тиража, для которого найден хотя бы один реальный слот отгрузки в выбранном периоде. Именно этот размещаемый тираж показывается как «Максимальный тираж», а теоретический предел хранится в результате сервиса отдельно.

Если у маршрута нет операций с положительной трудоёмкостью, возможный тираж считается 0, ограничивающий участок не заполняется.

Для проверки дат отгрузки сервис перебирает даты внутри выбранного периода и для каждой даты запускает планировщик на временном календаре. В календарь предварительно загружаются уже сохранённые дневные размещения за период. Если симулированный заказ заданного тиража помещается к проверяемой дате отгрузки, дата попадает в список доступных слотов. Симуляция использует дату начала планирования, равную началу выбранного периода, и не пишет результат в SQLite.

## Пересчёт

Пересчёт запускается автоматически после сохранения изменений в справочниках/заказах и вручную кнопкой «Пересчитать план» в боковой панели.

При пересчёте:

1. создаётся запись запуска пересчёта со статусом `running`;
2. текущий план читается из SQLite как предыдущий снимок;
3. сохранённые плановые операции и конфликты очищаются;
4. строится новый план по активным участкам и планируемым заказам;
5. успешные заказы получают статус `Запланирован` и рассчитанную дату запуска;
6. конфликтные заказы получают статус `Конфликт планирования`, а рассчитанная дата запуска очищается;
7. сохраняются изменения плана типов `created`, `removed`, `rescheduled`;
8. запуск пересчёта завершается статусом `completed` и краткой сводкой.
