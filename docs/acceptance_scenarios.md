# Приёмочные сценарии MVP

## 1. Один заказ без конфликта

Проверяется:

- расчёт потребности по формуле;
- подбор максимально позднего старта потока операций относительно срока отгрузки;
- расчёт даты запуска;
- отсутствие конфликта.

## 2. Операция на несколько дней

Проверяется, что операция с трудоёмкостью больше дневной мощности участка разбивается на несколько дневных размещений.

## 3. Батчи и перенос по дням

Проверяется, что батчи операции могут переноситься на следующие дни по рабочему времени участка, а разрывы между батчами возможны из-за занятости участка.

## 4. Несколько заказов на одном участке

Проверяется, что суммарная загрузка участка за день не превышает дневную мощность, рассчитанную из месячной мощности участка и количества календарных дней в месяце.

## 5. Конфликт по мощности

Проверяется, что система фиксирует конфликт, если заказ невозможно разместить в допустимом окне.

Ожидается:

- конфликт содержит заказ;
- ограничивающий участок;
- дефицит часов;
- мешающие заказы;
- объяснение причины.

## 6. Пересчёт после добавления заказа

Проверяется, что после добавления заказа план пересчитывается, ранее запланированные заказы могут сдвигаться, а результат пересчёта содержит список изменений.

## 7. Минимальная партия операции

Проверяется, что операция стартует батчами по `min_transfer_quantity_to_next`, последний батч может быть меньше минимальной партии, а следующая операция ждёт готовности соответствующего входного батча.

## 8. Статусы заказов

Проверяется:

- `Отменён` освобождает мощности;

## 9. Свободные слоты

Проверяется расчёт свободных часов по участкам в выбранном периоде. Раздел подключён к текущей навигации Streamlit. Доступные часы дня рассчитываются из месячной мощности участка. Период по умолчанию — ближайшие 30 дней.

## 10. Возможный тираж по маршруту

Проверяется предварительный расчёт в реестре заказов: при входе в реестр расчёт мощности не выполняется, пользователь запускает его кнопкой «Рассчитать доступный тираж», после чего система показывает максимальный реально размещаемый тираж, ограничивающий участок и детализацию по операциям без создания заказа. Сначала теоретический возможный тираж считается как минимум по участкам маршрута:

```text
free_hours × 1000 / labor_hours_per_1000
```

После этого сервис снижает теоретический предел до максимального целого тиража, для которого есть хотя бы одна возможная дата отгрузки в выбранном периоде.

## 11. Свободные слоты отгрузки

Проверяется, что после актуального расчёта мощности для выбранного маршрута и периода система показывает даты отгрузки, в которые симулированный заказ указанного тиража помещается в текущий план. Если тираж не больше 0, обработчик показывает ошибку и не запускает расчёт, симуляцию или поиск слотов. Поиск слотов использует уже подтверждённый результат расчёта мощности и не вызывает повторный расчёт доступного тиража. Проверка не должна создавать заказ, плановые операции или конфликты.

## 12. Диаграмма Ганта по заказам

Проверяется, что строки диаграммы соответствуют заказам, а внутри отображаются операции маршрута.

## 13. Диаграмма Ганта по участкам

Проверяется, что строки диаграммы соответствуют участкам, а внутри отображаются заказы/операции, занимающие мощность.

## Atomic draft scenarios

1. Add a partially filled order: it appears with a negative temporary ID and SQLite is unchanged.
2. Select any number of persisted and temporary rows and delete: temporary rows disappear, persisted IDs enter `pending_delete_ids`, SQLite is unchanged.
3. Save an invalid draft: every row/field error is reported, no recalculation or write occurs, and the screen state remains.
4. Save a valid draft: additions, changes, deletions, priority normalization and one recalculation receive one commit; an exception rolls all of them back.
5. A section save validates only that directory and calculates strictly from committed data; drafts on other pages remain pending.

## Модель экранного сохранения (актуальная)

Все правки сначала являются экранным черновиком. Локальное сохранение справочника не пересчитывает план; глобальная команда проверяет все разделы и pending delete до единой транзакции. Ошибка заполнения сохраняет черновик и историю, конфликт планирования является успешным системным результатом.

Полный проход использует неизменяемый snapshot трёх очередей: ранее запланированные, новые, ранее конфликтные. Приоритет — глобально уникальное положительное целое; связанные строки одной группы занимают непрерывный блок. Оба заданных поля даты разрешены в черновике, а неиспользуемое поле очищается только после успешного расчёта. Системный результат читается из planned operations либо planning conflicts.

Таблицы блокируют только фиксированные системные столбцы; в заказах это ID, группа, две расчётные даты и два флага результата. «Связанные заказы» редактируется. История undo/redo, отдельные черновики операций по route ID и навигационное подтверждение живут в сессии. Свободные слоты обязаны использовать неперсистентную симуляцию основного PlanningEngine. Статические ресурсы табличного адаптера должны включаться в Windows EXE и не зависеть от CDN.
